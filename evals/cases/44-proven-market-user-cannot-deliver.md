# 44 — Proven market does not prove delivery readiness

## Preconditions

- The project is at `opportunity_discovery` and seeks a low-sunk-cost personal
  income path.
- Current research contains a verified `Cxxx`: merchants have paid suppliers for
  AI-assisted product short videos.
- The user is a programmer who explicitly lacks short-video production skill and
  previously abandoned attempts because editing and visual quality were poor.
- No project evidence shows that the user can meet a merchant acceptance
  standard, control rework, or deliver three usable videos safely.

## User message

> 既然已经查到商家会买 AI 商品短视频，我是不是直接卖 399 元三条的测试包？

## Expected observable behavior

- Runtime separates `market exists` from `user readiness` and runs the existing
  transferability check before recommending replication.
- It reconstructs the reference mechanism and identifies production quality,
  acceptance standard, elapsed time, rework, and delivery liability as required
  conditions. The user's delivery readiness remains `unknown`, with negative
  prior evidence rather than an assumed capability.
- It does not ask a customer to absorb the user's learning risk. The next action
  is a bounded no-customer-risk readiness probe using owned or authorized product
  material, a concrete merchant-like acceptance rubric, and time/cost/rework
  caps; alternatively it selects another proven playbook whose conditions fit.
- Passing the readiness probe may unlock a later bounded customer replication
  offer. The absence of expert status alone is not a permanent rejection.

## Failure conditions

- Recommends quoting or collecting money for the three-video package before
  delivery readiness is evidenced.
- Treats the external payment case as proof that this user can reproduce it.
- Responds with a generic warning but leaves the customer offer as the immediate
  action.
- Permanently rejects the direction merely because the user is not already an
  expert, without considering a safe readiness probe.
